# Browser playback feasibility ? 2026-11-23/24

This is an implemented laboratory prototype, not the completed Spotify-style experience. It preserves com.allen.vybe, existing Compose screens, Android OAuth, YouTube search and cloud playlist operations. No substitute catalogue was added. Device results below distinguish the original HTML-audio fixture from YouTube. Earlier research documents describe the previous baseline and are superseded here where behavior changed.

## Implementation

Previously `MuseApp` routed every `Source.YOUTUBE` song through `ACTION_VIEW`; Android consequently chose the external YouTube application. Song taps now explicitly open `BrowserMusicActivity` inside VYBE. The activity passes video IDs and the selected search/playlist queue (bounded to 100 entries), pauses native sample playback, and uses the retained WebView engine for the ordinary mobile YouTube webpage. The original plain BrowserPlaybackActivity remains a diagnostic fixture surface. Channel, privacy and explicit cloud-playlist links retain their existing behavior. The latest native player covers the webpage with an opaque artwork/control surface; the diagnostic lab still exposes it; this is not an IFrame API player or stream-extraction approach. Autoplay is requested and WebView's gesture requirement is disabled for this user-initiated playback surface; YouTube may still require interaction or consent.

`BrowserPlaybackService` owns the WebView independently of the activity, with a MutableContextWrapper that drops the activity reference when detached. A media-playback foreground service supplies a separate platform `android.media.session.MediaSession`, MediaStyle notification, audio-focus handling, and a bounded partial wake lock while media is observed playing. It does not wrap the webpage in a pretend Media3 Player. The native sample Media3 service is retained independently.

Every 750 ms, fixed JavaScript reads the top document's HTMLMediaElement paused/ended/readyState/currentTime. Play/pause execute fixed DOM commands; next/previous navigate the native browser queue. State is observed before marking commands acknowledged, with a five-second command timeout. Navigation generations and observation request IDs reject obsolete callbacks. Navigation resets outstanding observation ownership, and a five-second watchdog recovers a lost callback and reports unknown state instead of a stale playing state. A service dump exposes sanitized position, observation timestamp, host, queue index and filter counters; it contains no access tokens, account identifiers or page text. Browser cookies are separate from REST authorization; OAuth tokens are never injected into a page. Android OAuth does not sign the WebView into YouTube; private, age-restricted or region-restricted videos can remain unavailable in that separate browser session.

The browser uses HTTPS only, validates certificates, denies webpage permission requests, disables file/content access, disallows mixed content and third-party cookies, and exposes no JavascriptInterface. Browser media controls apply to the top frame only. No UA spoof, DRM bypass, audio extraction, hidden IFrame or external YouTube playback intent is used. The latest browser-only experiment overrides WebView window visibility and installs origin-restricted document-start visibility getters/listener interception. These are experimental website interventions, not Brave WebContents media patches.

The existing generic diagnostics fixture remains available. Two small buttons in Browser lab open the new HTML-audio/Rust proof and a YouTube playback test. The fixture serves original dawn.wav through WebViewAssetLoader and an actual HTML audio element. It is independent of ExoPlayer; fixture success is never counted as YouTube success.

## Custom music-player UI and lyrics

The song-tap path now opens a native Compose music player using the existing VYBE theme. It supplies actual search/playlist title and creator metadata, a native progress/seek bar, play/pause, previous/next, selection from the current queue, and a lyrics panel below the controls. A browser mini-player on the existing Home/Search/Library surface reopens this player and sends play/pause/next to the same browser service; it does not start native sample audio. The latest song screen renders song artwork, a round creator-channel image, native progress/transport controls and lyrics. The WebView remains laid out behind an opaque native surface. Touch and accessibility access to the covered webpage are disabled. Diagnostic Browser lab remains separate. Creator images come from an additional native YouTube channels.list request, batched by 50 IDs; unavailable images do not discard search results. A page-DOM avatar is a fallback. Song and mini-player artwork use HTTPS YouTube thumbnail URLs. Bounded downloads, image dimensions and an in-memory bitmap cache limit resource use. Home/Search/Library and cloud playlist operations are preserved.

Automatic lyrics now use [LRCLIB's public v1 API](https://lrclib.net/docs). Song metadata is sent to LRCLIB without Google credentials. It supports synced LRC and plain lyrics; no import is required. YouTube title suffixes and channel Topic/VEVO suffixes are cleaned, then normalized title/artist and a duration within three seconds must match. Nonmatching recordings explicitly show unavailable lyrics; text is never fabricated. Metadata from arbitrary uploads is imperfect and coverage is incomplete. Results are cached in memory for the current process. Requests identify the local development client; a real project/contact URL and provider registration should be configured before distribution. Rate-limited responses do not trigger retry loops. Previously stored local LRC remains readable for compatibility and controlled tests, but import is no longer the main user flow.

LRCLIB's publicly accessible API is not a blanket licence to redistribute copyrighted lyrics commercially. Distribution requires resolving lyrics rights/provider terms and the public client identity; do not treat a working network request as that clearance.

## Rust filtering proof

The pinned published artifact `io.github.mlm-games:adblock:0.1.3` is integrated, rather than just proposed. Its Kotlin 2.4 module metadata failed with this project's Kotlin 2.2 compiler. A Java-only `filter-native` Android module now hides that dependency behind a small Java API; the wrapper's transitive stdlib is excluded and existing Kotlin 2.2.10 is retained. No compiler metadata check is suppressed. Only the small consumed wrapper API has been tested for runtime compatibility; reproducing the native build remains a release prerequisite.

AAR SHA-256: `8473059d1fb8d1407baff81cdbda12f14d0d655b4f0dd12236d5808d60c73018`. Inspection found real ELF binaries for arm64-v8a, armeabi-v7a, x86 and x86_64. ELF PT_LOAD alignment is 16384 for both 64-bit binaries and 4096 for both 32-bit binaries. Only arm64 has been exercised on this phone; this is not a four-ABI or 16 KB-device certification. MPL licence and source provenance are bundled under assets/licenses. A full native transitive licence inventory/SBOM and reproduction of the prebuilt binary remain outstanding.

There are two independent engines. The first retains the original bounded tracker/exception/CSS/scriptlet fixture rules for deterministic JNI tests. The second compiles bundled official EasyList (2,057,191 bytes) and EasyPrivacy (1,521,775 bytes) snapshots off the main thread and enforces network rules on browser subresources, including the ordinary YouTube website research surface. Initial browser navigation is withheld if those filters cannot initialize; they are not silently disabled. Matching returns an empty blocked response and increments separate list-match counters. Known resource types come from request headers where available, otherwise bounded URL/Accept heuristics. Main-frame navigation is not subject to list matching.

Basic domain cosmetics are applied as a generated stylesheet after page load. The only loaded scriptlet is the original fixture marker. No general uBlock/Brave scriptlet inventory, redirects/response rewriting, remote include resolver or updater is implemented. The unused third-party scriptlet bundle automatically merged from the wrapper AAR is overridden by an original empty inventory; this exclusion was verified inside the APK. That bundle is not mistaken for an audited usable dependency.

The EasyList authors are attributed and the CC BY-SA 3.0 licence is bundled. Exact source URLs, byte lengths and SHA-256 hashes are recorded in `assets/filters/PROVENANCE.json`. These are unmodified community-list snapshots, not the complete Brave component catalogue. A test fixture requests a known advertising URL through the real WebView interception callback; a local fallback prevents actual advertising content from loading if filtering fails, and the test requires a real list-match counter increment.

Browser-wide filtering is now implemented beyond the original host-only fixture. It is a browser research path, not filtering applied to an official IFrame API player. This does not exempt VYBE's overall API-client design from YouTube policies. **YouTube video-ad suppression and exact Brave equivalence remain unproved.** Blocking a known advertising request does not prove removal of pre-roll, mid-roll or server-inserted video advertising.

## WebView limitations and Chromium comparison

Android's [WebViewClient request callback](https://developer.android.com/reference/android/webkit/WebViewClient#shouldInterceptRequest(android.webkit.WebView,%20android.webkit.WebResourceRequest)) lacks Chromium's complete request pipeline: no request body, incomplete resource-type/frame context, no general response-body transform, no subsequent redirect URL callbacks, and no callbacks for javascript/blob URLs. Service workers use a separate interception surface and are not configured here. WebSocket and same-origin/server-inserted video advertising are not reliably addressable through this hook. Guessing type from URL/Accept cannot recreate browser request metadata. The prototype filters ordinary browser subresources too, using incomplete type heuristics; the callback limitations still apply.

Cosmetic filtering is DOM work, separate from network filtering. Scriptlets are executable code and require a trusted resource inventory, correct frame/origin/document-start handling and a permission model. This proof runs a bounded original scriptlet at fixture page-finish; it does not implement the complete Brave/uBlock document-start/frame lifecycle. A generic browser would need AndroidX WebKit feature checks, navigation-bound origin restrictions and worker/frame coverage.

A retained WebView and foreground service can keep Java ownership alive, but do not guarantee renderer execution, website consent, entitlement, autoplay, audio routing or background-video survival. Device use exposed an observation callback lost around a YouTube queue navigation. The observer now resets on navigation, retries after a five-second watchdog and publishes STATE_NONE for stale observations. This detects missing telemetry; it cannot force a hung renderer to execute. Compare timestamp and advancing media position, not only session state. It has no cross-origin iframe control, page-native MediaSession action interception, rich browser queue reconciliation, durable browser queue restoration, automatic queue advancement, browser search-by-voice or process-death recovery. The ten-minute wake-lock cap is intentional for a lab, not an all-night playback guarantee. An idle lab service remains until Stop or system termination. Battery/thermal/memory and multi-hour screen-off tests are outstanding.

Further actual source inspection found `components/browser_ui/media/android/java/src/org/chromium/components/browser_ui/media/BraveMediaSessionHelper.java`, `android/java/org/chromium/chrome/browser/media/BraveYouTubePictureInPictureController.java` and `browser/android/youtube_script_injector/youtube_script_injector_tab_helper.cc`. The helper reads Chromium's `disable-background-media-suspend` command-line switch, applies host-specific pause suppression and preserves notification/session state; the PiP controller explicitly handles screen-lock interruptions and the background-playback preference. These depend on WebContents, Chromium MediaSessionImpl and browser startup/profile infrastructure, which public Android WebView does not expose. VYBE does not force a playing state or assume a forged notification proves continuing media.

Brave is Chromium with browser/renderer/network lifecycle integration and its own media policy. A Brave/Chromium fork could supply deeper request/frame/worker and media hooks, at substantial build, distribution and ongoing security-update cost. Importing adblock-rust does not import these capabilities. WebView is sufficient for the controlled browser/filter/media bridge proof. Whether it is sufficient for reliable YouTube background playback must be decided from the YouTube-specific results, not from the fixture. No Brave fork was built here; necessity or success of such a fork is not established by source inspection.

For the user's exact Brave requirement, the current engine is **not sufficient**: Brave also has its full list/component resource catalogue, engine features, per-frame document-start scriptlets, exact network/worker/initiator context, exception/mode policy and Chromium media lifecycle hooks. Those cannot be reproduced exactly by this WebView callback and the published Rust wrapper alone. The native player UI and service snapshot/command boundary can be retained around a future Chromium embedder; changing catalogue is not required.

A full Brave/Chromium Android build was not performed. The [official Chromium Android build instructions](https://chromium.googlesource.com/chromium/src/+/main/docs/android_build_instructions.md) require a Linux x86-64 build environment and at least 100 GB free space; native Windows builds are unsupported. WSL Ubuntu and Kali are installed here, but the checked host drive had only 29,489,352,704 available bytes (about 27.5 GiB). No large checkout or system cleanup was started. A prepared Linux build volume with sufficient capacity and a Chromium embedder/security-update plan are concrete prerequisites to that next prototype, not reasons to substitute another music catalogue.

## YouTube policy implications

[YouTube API developer policies, section III.I](https://developers.google.com/youtube/terms/developer-policies) restrict interference with advertisements and official player functionality, audio/video separation, and background playback through API clients. In particular, ad suppression in an official API player is prohibited. Browser filtering is enabled in the isolated ordinary-website research engine, and is not injected into an official IFrame API player. The official REST client is kept separate from browser credentials and playback. The ordinary YouTube webpage and REST playlist client have separate playback/credential implementations, but this does not establish that combining API discovery with browser playback is exempt from API-client policies. Personal use is not an exemption.

The [ordinary YouTube Terms](https://www.youtube.com/static?template=terms) also govern website access and restrict unauthorized interference/circumvention. A browser engine change cannot resolve contractual restrictions or guarantee service compatibility. No claim is made that the requested ad-free/background YouTube product is policy-compliant. This is a technical research record, not legal advice.
